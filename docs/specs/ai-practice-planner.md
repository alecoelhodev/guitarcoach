Implement an AI Practice Planner feature using the OpenAI Responses API.

## Goal

Allow an authenticated user to describe the guitar practice routine they want in natural language, for example:

"Create me a 30-minute blues practice routine focused on bending and improvisation."

The AI should:

1. Understand the user's request.
2. Use application data when useful.
3. Use OpenAI's web search tool when external guitar-learning information would improve the plan.
4. Produce a structured practice-plan response.
5. Ask for confirmation before persisting the routine.
6. After confirmation, call a custom `create_routine` tool that uses the existing application service layer.

Use the OpenAI Responses API. The implementation must demonstrate:

- Structured Outputs
- At least one custom function tool
- At least one OpenAI built-in tool (`web_search`)
- Multi-step tool execution
- Safe persistence through existing NestJS business logic

Do not use the AI provider to write directly to PostgreSQL.

## Feature API

Add an authenticated endpoint similar to:

POST /api/v1/ai/practice-planner

Request:

{
  "prompt": "Create me a 30-minute blues routine focused on bending and improvisation."
}

The endpoint should send the request through an `AiPracticePlannerService`.

The authenticated user ID must come from the session/authentication context and must never be supplied by the model.

---

## Structured plan

Before creating anything, the AI must return a structured plan equivalent to:

{
  "title": "30-Minute Blues Practice",
  "summary": "Practice bending accuracy and blues improvisation.",
  "totalDurationMinutes": 30,
  "tasks": [
    {
      "title": "Warm-up",
      "description": "...",
      "durationMinutes": 5
    },
    {
      "title": "Bending practice",
      "description": "...",
      "durationMinutes": 10
    },
    {
      "title": "Blues improvisation",
      "description": "...",
      "durationMinutes": 15
    }
  ],
  "requiresConfirmation": true
}

Define this using a strict schema compatible with the Responses API Structured Outputs capability.

Validate that:

- title is present
- at least one task exists
- task durations are positive
- total task duration matches or reasonably satisfies the requested duration

Do not trust model output without application-side validation.

---

## OpenAI built-in tool

Enable OpenAI `web_search`.

The model may use web search only when external information materially improves the routine, such as:

- finding a useful guitar technique reference
- researching an unfamiliar technique
- grounding practice recommendations

Do not require web search for every request.

The core feature must still work when web search is unnecessary.

---

## Custom tool

Implement a custom tool named:

create_routine

Suggested input:

{
  "title": "30-Minute Blues Practice",
  "notes": "Generated by AI Practice Planner",
  "tasks": [
    {
      "title": "Warm-up",
      "description": "...",
      "durationMinutes": 5
    }
  ]
}

Requirements:

- The tool must call the existing NestJS routine creation/application service.
- Reuse existing DTOs, validation, transactions, and business rules where practical.
- The authenticated user ID must be injected by the application, not accepted from the model.
- Do not expose Prisma or generic database operations as AI tools.
- Do not allow arbitrary SQL or raw entity writes.

---

## Confirmation flow

Do not persist the generated routine immediately.

First response:

1. Generate the structured plan.
2. Return the plan to the client.
3. Return enough state to safely continue the interaction.

The client/user must explicitly confirm before `create_routine` is executed.

Example confirmation flow:

Request 1:
"Create me a 30-minute blues routine."

Response:
{
  "status": "awaiting_confirmation",
  "plan": { ... }
}

Request 2:
{
  "confirmation": true,
  "previousResponseId": "..."
}

Then:

1. Continue the Responses API interaction.
2. Allow the model to call `create_routine`.
3. Execute the custom tool server-side.
4. Return the final persisted routine information.

Use the Responses API conversation/state mechanism supported by the current OpenAI SDK rather than manually reconstructing model state when possible. Verify the current official OpenAI documentation before implementing API-specific details.

## Error handling

Handle at minimum:

- OpenAI timeout
- OpenAI unavailable
- malformed/invalid structured output
- unsupported tool call
- web-search failure
- routine validation failure
- routine persistence failure
- user declines confirmation

AI failures must not affect unrelated application endpoints.

Use reasonable request timeouts.

Do not implement complicated retry orchestration.

---

## Security

- Never expose the OpenAI API key to clients.
- Read credentials from environment configuration.
- Do not send unnecessary personal or sensitive user data to OpenAI.
- Never allow the model to choose another user's ID.
- Validate all tool arguments before executing them.
- Keep tool permissions narrow.
- Do not expose generic database, filesystem, shell, or HTTP-request tools.

---

## Tests

Add focused tests covering:

1. A normal prompt produces a valid structured plan.
2. User ID is derived from authentication.
3. The routine is not persisted before confirmation.
4. Confirmation triggers `create_routine`.
5. `create_routine` delegates to the existing routine service.
6. Invalid tool arguments are rejected.
7. Model-generated durations are validated.
8. OpenAI failures are handled gracefully.
9. Web search is optional and does not run for every request.
10. AI cannot supply or override `userId`.

Mock OpenAI calls in unit tests. Do not require live API calls for the normal test suite.

## Out of scope

Do not add:

- frontend UI
- autonomous routine creation without confirmation
- vector databases/RAG
- embeddings
- MCP
- RabbitMQ
- background jobs
- AI-generated audio
- direct AI database access
- multiple AI providers
- complex agent frameworks
- unrelated refactoring

Prefer the official OpenAI SDK and Responses API directly over adding an agent framework unless the repository already uses one.
